# 리뷰
1. Spark의 AQE가 엔지니어가 Spark를 최적화하기 위해 지표를 보고 여러 방법을 적용하면서 실험하는 과정을 자동화했다는 느낌을 받았다.
    - Spark의 AQE가 하는 일이 과거 엔지니어들이 직접 하는 일이라는 것을 느낌.
    - "어떤 문제를 해결하기 위해 어떻게 지표를 잡고 어떤 방법으로 해결하였는지"의 흐름을 간접적으로 볼 수 있었다.
    - Spark의 문제 정의 / 해결 방식이 꼭 데이터 엔지니어링에만 적용되는 것이 아닐 수 있겠다라고 생각하게 되었음.
    - 최종 프로젝트를 위한 문제 정의 과정도 "어떤 문제인지 어떤 지표가 핵심인지"도 비슷하다는 느낌을 받았다.
    - Spark의 최적화 작동방식을 잘 알면 다른 것을 최적화할 때에도 비슷하게 방식을 적용해볼수도 있겠다는 막연한 생각을 하게 되었다.

# 회고
## Keep
1. 열심히 쓰기. 펜으로 적고, 없다면 노트북으로라도, 없다면 휴대폰으로라도
    - 쓰다보면 정리가 잘 된다.
    - 일단 쓰고보자.
    - 쓰고 팀원들에게 보여주자. -> 말로만 하는 것보다 팀원들의 이해도가 올라가는 느낌, 그리고 더 많은 피드백이 온다.
    - 날짜와 시간을 적어두자. (삶속에서 자연스레 타임박싱하기 좋아짐.)

## Problem
1. 빠른 피드백 주기
    - 빠른 의사결정이 빠른 피드백의 핵심인 것 같다.
    - 의사결정을 하고 실패하고 다시 하는 비용 vs 의사결정의 퀄리티를 올리는 시간
        -> 보통, 전자가 더 비용이 낫다.
    - 의사결정을 위해 여러가지를 나열하기
        - 여러가지를 비교하기 -> 기록하기 -> 실패했을 때 적어둔 것중에 바로 시도해볼 수 있는 것도 잇을 것이다.
