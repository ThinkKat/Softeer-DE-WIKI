# 리뷰
1. 프로젝트 피드백 - API 설계 시 usecase
    - usecase를 생각할 때, 전체적인 비즈니스의 흐름도를 더 구체적으로 생각해야함.
    - 실제 업무를 하게 된다면?
        - 해당 업무를 하는 사람을 만나서 물어봐야함.
            - 과연 쉽게 알려줄 것인지... -> 그 사람의 시간을 뺏는 것이기 때문에 설득을 해야할 수도.
            - usecase를 생각한다는 건 해당 업무를 하는 사람의 입장이 되어봐야 함.
            - 결국, 문제 정의할 때처럼 **어려움을 겪는 지점**을 정확히 파악해야하는 것이 중요해진다.
            - 이를 파악하면 설득에 힘이 실릴 수 있고, API 제작에도 도움이 될 수 있음.

2. Shuffle, Shuffle, Shuffle
    - 결국, 분산 환경에서 데이터 처리 하는데 가장 큰 병목은 네트워크 I/O.
    - "셔플 작업을 어떻게 피할 수 있을까?"
        - shuffle 작업을 피하기 위한 각고의 노력의 산물을 spark에서 발견할 수 있다.
        - 오늘 배운 LocalShuffleReaderExec도 이 질문의 결과
        - 여기서 다시 나온 data locality라는 개념이 반가웠다.
        - data locality가 중요하다는 사실을 다시 한번 상기할 수 있었다.
